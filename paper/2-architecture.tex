\section{System Architecture}
\label{sec:architecture}

The architecture of \modora is designed to transform unstructured, multimodal documents into a structured knowledge hierarchy while providing an interactive and verifiable user experience. As illustrated in Figure~\ref{fig:arch}, the system is vertically organized into three layers: the \textbf{User Interaction Layer}, the \textbf{\modora Service Engine}, and the \textbf{Three-Stage Core Pipeline}.

\subsection{User Interaction Layer}
To bridge natural language queries with structured document trees, \modora provides an integrated environment featuring three specialized modules:

\runin{File Manager} Handles multimodal document ingestion and semantic tagging. \xbr{A persistent global library enables cross-session document reuse, eliminating redundant preprocessing.}%It maintains a persistent global library, enabling cross-session document reuse and eliminating redundant preprocessing.

\runin{Chat Engine} Supports complex QA with \textit{Interactive Grounding}. This feature allows users to trace AI-generated answers back to original PDF layouts via automated coordinate-based highlighting, ensuring the reasoning process is verifiable.

\runin{Tree Visualizer} Facilitates human-in-the-loop intervention by allowing users to manually edit the CCTree or issue natural-language restructuring instructions. It incorporates a \textit{Node Heatmap} (based on retrieval impact) to visually identify critical information hubs within the document hierarchy.

\subsection{\modora Service Engine}
Acting as the middleware bridging the user interaction layer and the core algorithmic pipeline, the Service Engine is optimized for multimodal RAG workloads. It orchestrates asynchronous preprocessing and retrieval tasks, tracks document processing status, and maintains a persistent knowledge base that stores per-document tags, semantic tags, and structural statistics for cross-session reuse.

\subsection{Stage 1: Multimodal Preprocessing}
Before indexing, documents undergo a rigorous enrichment process to capture multimodal nuances:

\runin{OCR with Robust Fallback} The backend first attempts structured OCR extraction through a configured OCR model, and automatically falls back to direct PDF block extraction when OCR loading or prediction fails. This design guarantees end-to-end document ingestion even under model failures.

\runin{Local-Alignment Aggregation} The system then applies rule-based structural analysis over OCR blocks: title blocks trigger new text components, figure blocks are paired with nearby captions, and header/footer/page-number/aside blocks are isolated into supplementary channels. The output is a ComponentPack with aligned content and pixel-level coordinates.

\runin{VLM-based Information Enrichment} For non-textual components (image/chart/table), \modora crops evidence regions and asynchronously invokes a multimodal LLM to generate a semantic triplet (Title, Metadata, Data). A bounded-concurrency design keeps throughput stable on large documents.

\subsection{Stage 2: Recursive Tree Construction}
The system organizes the enriched components into a logical hierarchy through a two-stage process:

\runin{Hierarchical Relationship Modeling} 1) \textit{Level Generation}: text titles are passed to an LLM that predicts Markdown-style heading depth, with retry and parser validation. 2) \textit{Main Branch Construction}: a stack-based constructor creates text hierarchy by title level and attaches adjacent non-text components to the current context. Duplicate sibling titles are disambiguated by automatic suffixing.

\runin{Supplementary Branch Isolation} Headers, footers, original page numbers, and aside texts are materialized as an independent \textit{Supplement} subtree under the root, preventing layout noise from contaminating main-body semantic retrieval.

\begin{sloppypar}
\runin{Bottom-up Metadata Summarization} To address information loss in long-document retrieval, metadata is generated with a bottom-up DFS pass. Leaf text nodes first receive keyword summaries, then internal nodes integrate child metadata into higher-level semantic descriptors. The target keyword count follows an attenuation-controlled growth model, preserving global coverage while avoiding summary explosion.
\end{sloppypar}

\subsection{Stage 3: Query-Adaptive Retrieval}
\modora uses a question-type-aware ``Parse-Retrieve-Verify'' workflow to balance recall and precision.

\runin{Query Parsing} The QA service first extracts page and position vectors from the query. If extraction fails, the query is treated as content-centric and routed to semantic/vector retrieval; otherwise it is routed to location-aware retrieval.

\runin{Location-Aware Path} For position-sensitive queries, \textit{LocationRetriever} traverses the CCTree with normalized bounding boxes and a 3$\times$3 page grid overlap test, returning nodes that intersect target regions and directly grounding answers to page coordinates.

\runin{Semantic + Vector Path} For content-centric queries, \textit{SemanticRetriever} recursively explores the tree by LLM-guided child selection and multimodal node relevance checks (text + cropped image). In parallel, \textit{VectorRetriever} performs embedding retrieval over CCTree nodes with persistent Chroma indexing and reranking. Their evidence is merged into a unified retrieval result.

\runin{Verification-then-Fallback} Retrieved evidence is used for final reasoning. If answer verification fails, the system falls back to whole-page reasoning (single-document mode). The engine then records retrieval provenance and updates node impact scores for subsequent interactive analysis.
